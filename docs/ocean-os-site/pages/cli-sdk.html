Ocean OS / CLI + SDK
slice 8 · cli-sdk
one-shot client + typed product contract

The CLI is the smallest daemon client; the SDK is the typed event vocabulary every richer client shares.

ocean-rs is a thin command-line client for health checks, one-shot prompts, and session inspection. ocean-agent-sdk is not a UI; it is the Rust crate that defines the product agent API consumed by the daemon, TUI, Ocean Surface, browser extension, and future native shells.

Workspace position

Both crates are first-class workspace members.

CLI crates/ocean-cli

The crate builds a binary named ocean-rs. It depends on ocean-core, reqwest, tokio, clap, and serde_json; it does not embed the runtime or provider layer.

Source: Cargo.toml:1-16, crates/ocean-cli/Cargo.toml:1-19

SDK crates/ocean-agent-sdk

The SDK crate defines serializable identifiers, requests, responses, tool primitives, turn events, and Longhouse extension events. It depends only on data/trait crates such as serde, uuid, chrono, anyhow, and async-trait.

Source: crates/ocean-agent-sdk/Cargo.toml:1-18, crates/ocean-agent-sdk/src/lib.rs:1-19

One-shot prompt flow

The CLI is intentionally synchronous from the user's point of view.

01

Parse command

clap reads --url from the flag, OCEAN_DAEMON_URL, or the default http://127.0.0.1:4780.

Source: crates/ocean-cli/src/main.rs:5-16

02

Build request

prompt joins positional args into one string, requires non-empty text, sets cwd from current_dir(), sets create_if_missing: true, and tags client_type: "cli".

Source: crates/ocean-cli/src/main.rs:54-74

03

Post to daemon

The CLI posts JSON to /v1/prompt and awaits a complete PromptResponse. It does not subscribe to /v1/agent/events.

Source: crates/ocean-cli/src/main.rs:75-82

04

Print result

Non-empty stderr is printed to stderr, stdout is printed as the visible answer, and a compact footer reports ok and wall time.

SDK design

The SDK carries product semantics, not runtime implementation.

This is the crate clients import when they want the same event vocabulary as the daemon emits.

Identifiers

AgentSessionId, AgentTurnId, and ToolCallId wrap UUIDs, implement display, and serialize cleanly.

Source: crates/ocean-agent-sdk/src/lib.rs:26-122

Sessions and turns

AgentSession is cwd-scoped and can hold an active turn; AgentTurn tracks prompt, status, start/finish timestamps, and optional error.

Source: crates/ocean-agent-sdk/src/lib.rs:123-170

Requests/responses

AgentTurnRequest captures prompt, cwd, optional guidance, room id, project id, client type, and optional session id. AgentTurnResponse returns ids, status, event prefix, and error.

Source: crates/ocean-agent-sdk/src/lib.rs:176-214

Typed event stream

AgentTurnEvent is the shared stream contract.

Renderable lifecycle

The enum covers turn start, text deltas, thinking deltas, tool call start/chunk/finish, turn finish with timing/token stats, session creation, component render/unmount, browser activity, and extension payloads.

Source: crates/ocean-agent-sdk/src/lib.rs:322-389

Forward-compatible extensions

Longhouse events ride inside AgentTurnEvent::Extension { extension: "longhouse", payload }, proving that feature streams can share /v1/agent/events without breaking clients that ignore unknown extensions.

Source: crates/ocean-agent-sdk/src/lib.rs:391-397, crates/ocean-agent-sdk/src/lib.rs:611-628

Serialization tests

The SDK tests assert tagged JSON serialization for turn_started, Longhouse wrapping/extraction, ToolCallFinished round-trip, and request serde.

Source: crates/ocean-agent-sdk/src/lib.rs:720-756

CLI vs SDK gap

The current ocean-rs binary uses ocean-core and the legacy /v1/prompt path. Rich streaming clients use ocean-agent-sdk and /v1/agent/events. A future CLI streaming mode could bridge that gap.

Source: crates/ocean-cli/src/main.rs:1-4, crates/ocean-agent-sdk/src/lib.rs:697-713

Legacy/core relation
Client implication

/v1/agent/sessions
Equivalent to GET /v1/sessions with turn metadata.

/v1/agent/events
Equivalent to GET /v1/events but scoped to AgentTurnEvent.

Local-first constraint

The CLI assumes the daemon is already running. It is a client process, not a daemon launcher and not a provider credential resolver.
