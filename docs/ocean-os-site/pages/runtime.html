slice 4 · runtime
agent loop + tool authority

The runtime is the turn engine: stream, decide, call tools, repeat.

ocean-runtime owns the provider-facing agent loop and built-in tool surface. It does not store sessions or serve HTTP; the daemon and ocean-agent wrap it with persistence, cancellation, permissions, and product event mapping.

Crate boundary

What the runtime exports.

The public API is intentionally small: configuration, tools, permissions, capability providers, and the loop entrypoints.

Loop entrypoints

run_agent starts from one user message; run_agent_with_history continues an existing transcript. Both return an AgentRun with messages, turn-limit status, and provider usage.

AgentConfig carries the selected model, thinking level, stream options, max turns, tool list, system prompt, and permission policy.

Turn loop

How one prompt becomes multiple model/tool rounds.

The loop runs until the model stops naturally, a tool terminates the run, or max_turns is reached.

01

Replay history

The latest user message is emitted, then the loop announces AgentStart. Existing transcript is passed in by ocean-agent, not loaded here.

02

Build model context

Each round constructs an ocean_protocol::Context with system prompt, trimmed messages, and tool definitions.

03

Stream provider

Execute tools

Append results

Capabilities

Tools are selected through a registry, not hardcoded in the loop.

This is the extension seam for built-ins, MCP, and future skill providers.

Provider-first design

CapabilityRegistry owns an ordered list of CapabilityProviders. On each turn, providers return tools for a SessionContext containing cwd and session id.

Source: crates/ocean-runtime/src/capability.rs:29-45, :65-80, :122-159

First provider wins

Tool names are deduped first-wins, with built-ins registered before later providers. That prevents an MCP server from overriding core tools such as bash.

Source: crates/ocean-runtime/src/capability.rs:116-121, :159-177

Default built-ins

The current built-in suite includes file tools, shell, search, web fetch, todo tracking, and component render/unmount/wait.

Source: crates/ocean-runtime/src/tools/mod.rs:25-40

Resolved by ocean-agent

The runtime loop receives a concrete Vec<Arc<dyn AgentTool>>. ocean-agent asks the registry for the session's tools immediately before configuring the run.

Source: crates/ocean-agent/src/lib.rs:441-456

Side effects

Tool side effects become client UI events after execution.

The tool trait itself returns content plus optional side effects; the loop emits them as events.

pub enum ToolSideEffect {
  Render { id, kind, props, replace },
  Unmount { id },
  BrowserActivity { active },
}

Why this matters

Component tools can mount dashboards, forms, diffs, and confirmations without every tool receiving a mutable event sender. Browser tools can also signal active/idle so clients such as a side panel can focus or release at the right time.

Source: crates/ocean-runtime/src/types.rs:11-42, crates/ocean-runtime/src/agent_loop.rs:232-258, crates/ocean-runtime/src/tools/component.rs:5

Safety model

The runtime has permission hooks, but policy lives above it.

Tool-level default

AgentTool::requires_permission() defaults to false. Read-only tools can stay quiet; mutating or side-effecting tools override this to ask the configured policy.

Source: crates/ocean-runtime/src/types.rs:84-100

Policy outcomes

A policy can Allow, AllowSession, or Deny. Session allows are remembered per tool name for the rest of that run; denied calls are appended as error tool results.

Source: crates/ocean-runtime/src/types.rs:55-80, crates/ocean-runtime/src/agent_loop.rs:155-188

Important boundary

The loop only asks the configured policy. The daemon decides which policy to pass for a given API path, request, or client mode. See the daemon page for the current /v1/agent/turns permission-mode note.

Cancellation path

The loop honors cancellation through StreamOptions::cancel; the daemon wires request cancellation into that stream option before calling ocean-agent.

Source: crates/ocean-runtime/src/agent_loop.rs:1-5, crates/ocean-agent/src/lib.rs:436-459

Context control

The runtime has two token-cost guardrails.

These are runtime-level protections before session persistence applies its own cap.

Context-window trimming

Before each provider request, the loop keeps the newest contiguous suffix that fits the model context budget after reserving system prompt, max output, and a 5% margin. Leading orphan tool results are dropped.

Source: crates/ocean-runtime/src/agent_loop.rs:335-407

Tool-result capping

The full tool output is emitted to the UI via ToolExecutionEnd, but text retained in the transcript is capped at 32 KiB per block to avoid resending giant outputs indefinitely.

Source: crates/ocean-runtime/src/agent_loop.rs:259-305
